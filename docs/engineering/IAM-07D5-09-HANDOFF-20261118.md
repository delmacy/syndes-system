## Bloqueios pendentes de alta prioridade

**IAM-07D5 — Unificar evidência HTTP real:** criar **um** laboratório Nest HTTP de negócio completo com JWT humano Keycloak assinado, Organizations live, Control PG17, tenant PG17 SQL002, modelo OpenFGA granular e efeito real do Inbox claim e Service stage advance na mesma jornada. Testar 200/401/403, claim/ticket stale, ownership de funil, audiência Manager e contexto A/B. Nenhuma rota deve existir em `main.ts` fora de modo CI descartável.

**IAM-07D6 — Revogação administrativa exclusiva:** implementar orquestração que escreve no tenant `revoked + epoch + outbox` no mesmo COMMIT, depois altera FGA e, se pertinente, Keycloak; preservar a outbox com retries e reconciliação. **Impedir alteração por caminhos paralelos** requer governança de tokens/grants/roles do próprio Keycloak/OpenFGA. Ausência dessa exclusividade é bloqueio operacional, não bug de SQL. Revogação de uma capability **não deve remover a Organization inteira**. Conciliação de target catalog FGA deve ser completa, auditável e negar na dúvida.

**IAM-07D7 — Cobrir todas as escritas e rotas:** mapear `Inbox.claim/transfer` e `Service.open/advance/assign/close/transferTeam` e as alterações CRM/Funis relacionadas. Cada efeito e evento auditável devem usar **o mesmo pinned transaction e o mesmo IAM epoch**. Testar corridas com revogação antes e durante lock; não duplicar SQL da engine, nem equiparar `inbox:assignment/write` à capability fina.

**IAM-08 — Administração:** API com JWT Manager/operador distintos e privileges mínimos, operation_id idempotente, registros administrativos sem PII, UI apenas se contratos estiverem aprovados.

**IAM-09 — Product Gate operacional:** roles SQL reais least-privilege, staging backup/restore real e rollback, canary sem alteração direta do realm antes do aceite, recuperação e auditoria diante de indisponibilidade, carga/soak multi-host/SSE broker, métricas p95 sob carga, anti-cross-tenant e UX com dados de negócio reais. Nunca ativar por testes de laboratório isolados.

## Protocolo de execução

- Código **somente pelo GitHub**, branches pequenas e PRs, CI central `.github/workflows/syndes-ci.yml` e `Syndes CI Gate`. Na fase atual `main` deliberadamente sem proteção rígida, mas sem aceitar CI vermelho.
- **Sem execução manual no servidor**, sem Docker deploy manual e sem alterações diretas de realm `syndes`, OpenFGA store operacional, Control/tenant DDL ou grants. Se chegar a Product Gate aprovado, CD exclusivamente via GitHub Actions.
- Respeitar `AGENTS.md`, WBS IAM e Issue #160, mantendo docs da biblioteca alinhados aos contratos reais. Não inventar capabilities, classes, UX ou features.
- Exigir testes unitários e integração PostgreSQL+Keycloak+OpenFGA real descartável para cada avanço; diferenciar stub de provider real e não atribuir p95 de CI ao produto.
- Em cada PR registrar SHA, link, run CI, jobs aprovados, marcadores novos, restrições e pendências; não declarar produção operacional sem evidência e autorização.

O caminho de **revogação tenant-first controlada** está provado no laboratório; o **bloqueio da produção** continua até que o Syndes monopolize/administre os escritores externos, aplique o fence em todas as operações e prove E2E/restore/rollback no ambiente de homologação. O próximo chat deve priorizar **IAM-07D5**, não novos módulos, telas ou refatorações cosméticas.
