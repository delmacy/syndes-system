# DevServer01 — WhatsApp gateway
This compose adds the Go/whatsmeow gateway to the existing external syndes-data network. No public gateway port.
Before boot:
1. Configure WHATSAPP_STORE_DSN to the dedicated PostgreSQL database used by the gateway. The database must exist; credentials need DDL to initialize Whatsmeow and its queues.
2. Configure separate high-entropy WHATSAPP_WHATSMEOW_TOKEN and WHATSAPP_WEBHOOK_TOKEN in the *gateway and Core Host deployments*. Keep secrets outside git and browser configuration.
3. Rebuild/redeploy Core Host with the WhatsApp module plugin installed and migrations 001 and 002 applied to each enabled tenant DB; turn on WHATSAPP_DISPATCH_ENABLED only after confirming the receiver exists.
4. Confirm core-host and whatsapp-gateway resolve one another on syndes-data.
5. Run: docker compose -f modules/whatsapp/deploy/compose.yaml config (with env configured), then docker compose -f modules/whatsapp/deploy/compose.yaml up -d --build.
6. Pair a dedicated test number in Workspace > Settings > WhatsApp numbers, inspect the inbound event storage and Inbox, verify disconnect and reconnect.
A Go test suite and a web build do NOT substitute for container startup/QR/live-message acceptance.

## WhatsApp QR connectivity repair — 2026-11-03
The gateway **already has internet egress** via Docker bridge `syndes-whatsapp-egress` (`internal=false`). Tests executed in the actual gateway container network namespace: WhatsApp DNS lookup succeeded, `https://web.whatsapp.com/` returned HTTP 200, HTTPS general connectivity returned HTTP 204, and a `wss://web.whatsapp.com/ws/chat` handshake opened successfully. Do not expose the private gateway port or deploy another gateway/PostgreSQL as a workaround.

**Root cause:** `GetQRChannel(request.Context())` tied the whatsmeow QR emitter's lifespan to a short-lived HTTP pairing request. The upstream QR library explicitly cancels the QR channel and disconnects the client when that context ends. It also rotates QR codes using its provided timeout (60s initially, then shorter intervals), not the previous hard-coded 160s expiry.

**Fix:** the Go gateway holds an independent, bounded pairing session per account; concurrent HTTP pairing requests return the current live code, and the session follows provider QR rotations. HTTP cancellation no longer cancels the pairing stream. The React UI auto-refreshes before expiration. The new release is gateway `syndes/whatsapp-gateway:whatsapp-cutover-20261103-qrfix` and frontend assets `/home/delmacy/syndes-releases/whatsapp-qrfix-20261103/workspace-dist`. Verified two authenticated pairing requests 3 seconds apart both returned HTTP 200 with the same active QR, with approximately 57 seconds remaining. QR content/tokens were never printed or recorded. Go race tests and Go + Workspace CI passed.

Pre/post snapshots: `/home/delmacy/syndes-snapshots/2026-11-03-whatsapp-qr-pre-fix` and `/home/delmacy/syndes-snapshots/2026-11-03-whatsapp-qr-post-fix`. Old release and image remain locally available for rollback. A real WhatsApp device must still scan the QR and establish a linked-device session before end-to-end receipt can be considered validated.

## WhatsApp replies from Inbox — 2026-11-03
**Confirmed root cause:** the previous Inbox POST `/v1/tenants/:tenantId/inbox/conversations/:id/replies` inserted an `outbound` `inbox_messages` row but did not queue or send a WhatsApp message. WhatsApp inbound reception already worked. The historical local-only outbound message is retained **without automatic retransmission**, to prevent unexpected duplicate/customer messages.

**Integration:** the WhatsApp plugin exports a tenant-aware outbound reply port to the Inbox module. Once JWT, tenant membership, FGA and conversation access are checked, a single PostgreSQL statement atomically inserts the outbound Inbox message, its audit event, and a tenant-scoped `whatsapp_outbox` intent, only for a matching enabled account and conversation assignment. The account and recipient are derived from an approved inbound WhatsApp event, never chosen by the browser. `003_whatsapp_outbound_inbox.sql` creates `whatsapp_conversation_routes` and gateway queue tracking. Older conversations are backfilled from *processed* tenant inbound events on their first new reply; any missing/mismatched route fails closed. New inbound events populate the route in the same SQL projection transaction.

**Delivery:** the trusted Core Host worker relays queued intents to Go using per-tenant/account HMAC and the Inbox message UUID as an idempotency key. The Go gateway persists outbound intent and sends from its already-paired WhatsApp session. A second status poll checks the actual gateway queue result before marking a tenant message as sent. Failed or uncertain Go deliveries are recorded as failed and **never automatically re-sent**. Retries of a lost queue-acknowledgement reuse the same idempotency key. The Inbox now shows `Na fila`, `Enviando`, `Enviada`, `Falha` or `Não enviada pelo gateway` for WhatsApp replies; the last label distinguishes older local-only replies.

**Validation:** backed up the tenant and gateway PostgreSQL databases as encrypted-access restricted dumps in `/home/delmacy/syndes-snapshots/2026-11-03-whatsapp-outbound-before`. Ran two actual tenant PostgreSQL SQL transactions that generated a test inbound route and a test outbound Inbox+outbox intent; both passed and were rolled back without sending any real WhatsApp message. WhatsApp unit suite: 27 passed; Inbox suite: 13 passed. New Core Host passed `/readyz` in an isolated canary before cutover. The in-place Traefik shadow deployment now uses Core image `syndes/core-host:whatsapp-outbound-status-20261103` and frontend `/home/delmacy/syndes-releases/whatsapp-outbound-status-20261103/workspace-dist`. The Go gateway was not recreated and its paired session was preserved. After cutover, Core `/readyz`, Go `/healthz`, HTTPS workspace and runtime all returned HTTP 200, and anonymous Inbox replies were rejected with HTTP 401. Post-cutover snapshots are at `/home/delmacy/syndes-snapshots/2026-11-03-whatsapp-outbound-after`.

**Acceptance remaining:** the user should submit a *new* WhatsApp reply from the assigned Inbox conversation, then check its delivery state and verify it appears on the intended device. The existing old reply must not be assumed delivered. Go's `sent` means WhatsApp's `SendMessage` call returned a message ID; it is not a read receipt or proof the recipient opened it. ## WhatsApp history, chat filters and bot safety — 2026-11-03

**Goal:** WhatsApp Web-like chat list/filters, history sync, and no bot response to groups, emoji reactions, old messages or messages sent by the user's own WhatsApp account.

**Implementation:** The Go gateway now consumes WhatsApp HistorySync events (including direct and group chat metadata without fake messages), and supports authenticated, tenant-bound, on-demand history requests of up to 50 older messages in a known chat. Supported text messages keep original timestamps, direction, chat JID, provider message IDs, and a historical source. Reactions, protocol changes and newsletters are filtered out. History, group and fromMe events carry bot_eligible=false; only live direct inbound regular text carries bot_eligible=true. No bot worker is deployed in this module: future automation must check this flag before generating a reply.

Migration 005_whatsapp_history.sql adds tenant-local is_group, unread_count, is_favorite, is_archived and history_sync_at to conversations, and source, bot_eligible and provider IDs to messages. Inbound event insertion and history projection use tenant/account validation and unique external message hashes for idempotency. The Inbox offers Todas, Não lidas, Favoritas, Grupos and Arquivadas, combined with the existing agent/status filters, a tenant-scoped server-side search and paginated load-more. Favorites and unread markers are Syndes-local; this feature is not a two-way WhatsApp read receipt sync.

**Known limit:** The first complete chat-list/history bootstrap is sent by WhatsApp when a companion device is paired. This device was paired before our history listener existed. A current linked session can request older batches only for already-known chats with an anchor message; unknown older chats cannot be guaranteed or retroactively listed without a new pairing bootstrap, which must NOT be triggered without user approval. Full media sync is also not implemented.

**Validation:** The canonical tenant PostgreSQL was migrated after taking restricted-access tenant and gateway backups.
